# MicroBot Labs — Dashboard Test Checklist v0.2

## 1. Purpose

This document defines the repeatable test checklist for the MicroBot PC Controller Dashboard v0.2.

The dashboard is currently designed to work in offline/mock mode, while preparing the future transition to Web Serial and real ESP32 hardware communication.

The goal of this checklist is to make every dashboard test clear, repeatable and honest.

A dashboard test is successful only if the operator can clearly identify:

- the current mode;
- the command sent;
- the response generated;
- the Master state;
- the NODE_01 state;
- the safety state;
- the raw protocol log;
- the simulation placeholder update;
- whether the test is simulated or hardware-based.

## 2. Current Dashboard Location

The dashboard is located at:

web/dashboard/index.html

To open it from the repository root:

open web/dashboard/index.html

## 3. Current Test Mode

For now, the default test mode is:

OFFLINE MOCK

This means:

- no ESP32 is required;
- no physical serial port is required;
- NODE_00_MASTER is simulated;
- NODE_01_LED_STATE is simulated;
- command responses are generated by JavaScript;
- the raw protocol terminal shows mock packets;
- the simulation placeholder updates from dashboard state.

This is not physical hardware proof.

It is dashboard, protocol, state and demo-flow validation.

## 5. Offline Mock Mode Test

Use this test when no ESP32 is connected.

Expected initial state:

| Field | Expected Value |
|---|---|
| Connection | CONNECTED / MOCK |
| Master | READY |
| Safety | NORMAL |
| Mode | OFFLINE MOCK |
| NODE_00_MASTER | READY / ONLINE |
| NODE_01_LED_STATE | IDLE / ONLINE |

## 6. Command Test Sequence

Run this command sequence from the dashboard buttons.

| Step | Command | Expected Dashboard Result | Expected Log Result | Status |
|---:|---|---|---|---|
| 1 | Start Offline Mock | Mode remains OFFLINE MOCK | MOCK_CONNECT event appears | To test |
| 2 | PING | Master remains READY | PONG-like response appears | To test |
| 3 | STATUS | Master/Safety values remain visible | STATUS response appears | To test |
| 4 | GET_NODE_TABLE | Node table packet appears | Node list appears in raw terminal | To test |
| 5 | SCAN_NODES | Scan packet appears | Expected/online node count appears | To test |
| 6 | SET NODE_01 ACTIVE | NODE_01 becomes ACTIVE | SET_LED response appears | To test |
| 7 | NODE_01 WARNING | NODE_01 warning state appears | telemetry/warning packet appears | To test |
| 8 | NODE_01 ERROR | NODE_01 error state appears | error packet appears | To test |
| 9 | STOP | Master/NODE_01 enter SAFE_MODE | STOP response appears | To test |
| 10 | RESET | System returns READY/NORMAL | RESET response appears | To test |
| 11 | EMERGENCY_STOP | Master enters EMERGENCY | emergency response appears | To test |
| 12 | RESET | System returns READY/NORMAL | RESET response appears | To test |

## 7. Visual Validation

During the test, verify:

| Visual Element | Expected Behavior |
|---|---|
| Header | Shows MicroBot Labs / PC Controller |
| Mode field | Shows OFFLINE MOCK during mock mode |
| Connection field | Shows CONNECTED / MOCK |
| Master field | Changes between READY, SAFE_MODE and EMERGENCY |
| Safety field | Changes between NORMAL, WARNING, SAFE_MODE and EMERGENCY |
| NODE_01 card | Changes between IDLE, ACTIVE, WARNING, ERROR and SAFE_MODE |
| Packet counter | Increases after commands |
| Warning counter | Increases after warning command |
| Error counter | Increases after error or emergency |
| Raw terminal | Shows TX-MOCK and RX-MOCK packets |
| Simulation placeholder | NODE_01 and Master visual states change |

## 8. Safety Validation

The dashboard must always make safety visible.

| Safety Command | Expected Result |
|---|---|
| STOP | Master enters SAFE_MODE, NODE_01 enters SAFE_MODE, Safety shows SAFE_MODE |
| EMERGENCY_STOP | Master enters EMERGENCY, Safety shows EMERGENCY |
| RESET | Master returns READY, NODE_01 returns IDLE, Safety returns NORMAL |

If STOP or EMERGENCY_STOP does not visibly change the dashboard state, the dashboard test fails.

## 9. Web Serial Preparation Check

The dashboard includes Web Serial preparation, but this should not be treated as hardware validation unless an ESP32 is physically connected.

When no ESP32 is connected:

| Action | Expected Result |
|---|---|
| Press Web Serial Hardware Only | Browser may request a port or show unavailable/error |
| No serial port selected | Dashboard should not be described as hardware-connected |
| Browser lacks Web Serial | Error should appear or mock fallback remains available |

Correct interpretation:

Web Serial preparation exists.

Incorrect interpretation:

Real ESP32 communication has been validated.

## 11. Pass / Fail Criteria

The dashboard test passes if:

| Criterion | Required |
|---|---|
| Dashboard loads | yes |
| OFFLINE MOCK mode is visible | yes |
| PING produces response | yes |
| STATUS produces response | yes |
| NODE_01 ACTIVE changes visible state | yes |
| STOP changes safety state | yes |
| RESET restores normal state | yes |
| Raw terminal shows packets | yes |
| Simulation placeholder updates | yes |
| No hardware claim is made | yes |

The dashboard test fails if:

| Failure | Reason |
|---|---|
| Dashboard does not load | Broken UI |
| Buttons do nothing | Broken command handling |
| Mode shows wrong state | Confusing public evidence |
| STOP does not change state | Safety failure |
| Raw terminal stays empty | No observable protocol behavior |
| Screenshot claims real hardware while in mock mode | Misleading evidence |
