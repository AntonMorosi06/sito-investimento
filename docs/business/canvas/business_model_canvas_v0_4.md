## 1. Purpose

This document translates MicroBot Labs into a Business Model Canvas.

The Business Model Canvas is useful because it forces the project to answer nine business questions: who is served, what value is offered, how users are reached, how relationships are maintained, how revenue could be generated, what resources are required, what activities matter, which partners are needed and what the cost structure looks like.

For MicroBot Labs, the canvas must be treated as a hypothesis map, not a final company plan. The project has strong documentation and software evidence, but it does not yet have real hardware validation, customers or revenue.

## 3. Customer Segments

The first customer segment is not the industrial robotics buyer. The first segment is the learner or evaluator: someone who wants to understand robotics through a complete path from idea to validated hardware.

### 3.1 Students

Students may use MicroBot Labs to understand embedded systems, modular robotics, telemetry and validation. The project can help them see how a technical system is structured beyond isolated exercises.

### 3.2 Makers

Makers may value a reproducible ESP32-based robotics project with dashboard, firmware and validation scripts.

### 3.3 Educators

Educators may use MicroBot Labs as a teaching demonstrator because it combines technical explanation, BOM, diagrams, dashboard and staged validation.

### 3.4 Professors and technical collaborators

Professors and collaborators are not traditional customers at first. They are validation partners. They can assess whether the project is technically coherent and help guide the next prototype.

### 3.5 Future incubators

An incubator may become relevant only after the project has real hardware evidence, a demo video and a clearer market target.

## 4. Value Propositions

The strongest value proposition is integration.

MicroBot Labs does not simply say "build a robot." It offers a staged ecosystem:

- documentation;
- firmware;
- dashboard;
- telemetry;
- simulation;
- validation tools;
- visual diagrams;
- BOM;
- evidence reports;
- future hardware path.

This gives the project a stronger educational value than a single hardware tutorial.

The secondary value proposition is honesty. The repo distinguishes between simulated, validated-offline and hardware-validated states. This is important because robotics projects often overclaim.

## 5. Channels

The first channel is GitHub. It is already active, public and structured.

The second channel should be a portfolio website or demo page that links to the repo and shows screenshots, diagrams and demo videos.

The third channel should be direct outreach to professors, makers and technical collaborators.

Future channels could include YouTube demo videos, technical blog posts, educational workshops and incubator applications.

## 6. Customer Relationships

The relationship model should be educational and transparent.

MicroBot Labs should not present itself like a polished commercial product yet. It should present itself as a serious, open, evidence-based technical project.

The best relationship style is:

- clear documentation;
- honest limitations;
- regular progress updates;
- open issues;
- reproducible steps;
- direct feedback requests.

## 7. Revenue Streams

Revenue is not validated yet.

Possible future revenue streams include:

1. educational kits;
2. paid workshops;
3. course material;
4. consulting/help for robotics demos;
5. sponsorship;
6. university project support;
7. future hardware bundle.

The first revenue experiment should be small. A paid workshop or guided build session is more realistic than selling a complete robotics product.

## 8. Key Resources

The most important resource today is not hardware. It is the integrated knowledge base.

Key resources include:

- GitHub repository;
- extensive documentation;
- dashboard source code;
- firmware baseline;
- validation scripts;
- visual assets;
- MicroBot architecture;
- roadmap;
- BOM;
- personal learning and development effort;
- future ESP32 hardware kit.

## 9. Key Activities

The key activities for the next phase are:

- buy v0.4 minimum hardware kit;
- validate real ESP32 NODE_00_MASTER serial output;
- capture logs;
- produce report;
- update evidence;
- create demo video;
- ask for external review;
- prepare NODE_01 LED physical validation;
- refine educational narrative.

## 10. Key Partnerships

The most useful early partners are not investors. They are technical validators.

Recommended partners:

- professor or teaching assistant;
- robotics student/collaborator;
- makerspace person;
- embedded systems mentor;
- electronics supplier only later;
- school/university only after demo is stronger.

## 11. Cost Structure

The first cost structure is small:

| Cost | Expected range | Timing |
|---|---:|---|
| v0.4 minimum kit | 60-130 EUR | immediate |
| domain/website | 10-30 EUR/year | optional |
| hosting | 0-15 EUR/month | optional |
| 3D printing | later | after physical design |
| drone parts | later | after ESP32 validation |
| legal/company costs | later | only if business path matures |

## 12. Canvas validation priorities

The most important hypotheses to test are:

1. Can an external person understand the repo in five minutes?
2. Can someone run the dashboard without help?
3. Can the ESP32 validation be reproduced?
4. Would students or educators find the staged approach useful?
5. Would a professor consider this a credible project?
6. Would someone pay for a guided robotics learning kit/workshop?

## 14. Conclusion

The current Business Model Canvas points toward an educational robotics/prototyping model, not an industrial robotics product.

The project should move from repository credibility to first hardware evidence, then from hardware evidence to a small educational/demo offer.
